# ontoKBv2 以 Codex Harness 为中心的企业级本体个人记忆库

版本 1.0 · 2026-09-28 · Miniproject 中文确认版

## 项目介绍

将 ontoKB 升级为以 Codex harness 为中心的个人记忆 Agent。主要使用方式是通过对话委托 Agent 收集、回忆、比较、审核和执行受控操作，并支持进度、必要审批、中途调整及恢复。普通用户无需设计 schema 或运维企业平台。以 `logos-code.zip` 为本体与治理蓝本，复用接入、发布、强类型执行和审计，将其能力转化为 harness 工具；保留 ontoKB 的资料、证据、阅读、个人立场、历史及 Obsidian 工作流。交付中心是 Agent harness，网页仅作为可选证据查看与审核辅助。

用户能够保存文章、视频转录、笔记或会议记录，自动获得结构化对象和可追溯论断；能够针对资料库或个人记忆提问，理解新证据对旧判断的影响，并通过受控操作纳入记忆、更新判断或完成任务。系统必须区分“资料说了什么”“系统校验了什么”和“用户相信什么”。

本项目的“企业级 ontology”指对象类型、强类型属性、关系类型、函数、Action、生命周期规则、权限策略、来源追溯和版本发布构成的可执行契约。只有图谱可视化、带标签的三元组、提示词或 YAML 定义不能验收。参考 Palantir 的本体概念，不宣称产品等同、兼容或认证。概念依据见官方 [Ontology 概述](https://www.palantir.com/docs/foundry/ontology/overview)、[Action Types](https://www.palantir.com/docs/foundry/action-types/overview) 和[对象权限](https://www.palantir.com/docs/foundry/object-permissioning/overview)。

## 基线及历史评估

基线是本次提供的快照，不假定它是 LOGOS 最新版本。以下判断基于静态源码检查；运行效果与精度尚待实测。

| 来源 | 可复用基础 | 需要升级的部分 |
|---|---|---|
| ontoKB | Schema.org 应用剖面、类型及关系校验、SQLite、来源证据、人工修正、版本冲突检查、个人记忆与判断历史、文章/视频接入、Obsidian 投影 | 属性级运行时契约、带工作区范围的稳定身份、通用 Action 执行、持久自动化、版本治理、完整评测和易用分发 |
| LOGOS ZIP | 强类型对象、Function/Action 定义、领域包、来源权威、状态与策略、Connect/Build/Review/Release、运行时路由和执行回执 | 将客服业务替换为个人记忆领域；加固契约加载及持久执行；验证安全与恢复；降低部署复杂度 |
| TEBIS meeting ZIP | 来源片段、候选审核、时间模型和显式注册表提供参考 | 避免声明与实现脱节、占位路径、仅记录而未执行的权限；抽出的 ActionItem 是业务对象，不是可执行 Action Type |

ontoKB 已有本体剖面和规则引擎中的局部“动作”，缺口在运营模型的完整性及强制执行。TEBIS 也有类型 schema 与 Action 声明，应依据具体执行缺口评价，不能笼统写成完全没有 ontology。详细文件证据和 ZIP 指纹见[来源评估](SOURCE_ASSESSMENT_ZH.md)。

## 产品范围与用户

面向研究者、学生、工程师和知识工作者，让用户拥有可靠的个人记忆，而不必成为本体管理员。首版为每个本地工作区一个拥有者，支持中文和英文内容及界面。这是待项目启动时确认的语言基线；日语及其他语言属于后续扩展。“人人可使用”意味着上手容易、流程可理解、数据可迁移、推理前提透明，不意味着支持所有格式、所有语言或自动判定所有事实真伪。

| 优先级 | 交付范围 |
|---|---|
| P0 功能试点 | Windows Codex 集成、skills 与限定工具、强类型本体运行时、接入队列、有据问答、个人记忆、内部 Action、迁移、隐私及可复现评测 |
| P1 v2 验收 | 完整质量门槛、持久定时接入与回顾、普通用户易用性、备份恢复、导出删除、稳定打包与运维 |
| P2 扩展 | macOS/Linux 产品包、认证共享服务、团队审批、更多连接器、OCR、原始音视频 ASR、企业 SSO/HA、外部回写 |

ontoKBv2 完整验收必须满足 P0 和 P1。P0 演示只能称为试点。核心代码应避免不必要的操作系统耦合，但仅能对已测试的产品包宣称跨平台支持。不会因为 WhisperLive 参考文档有 Netaccess，就默认本项目也必须交付该服务器或共享托管。

## Codex harness 使用与集成要求

主要验收路径是在 Codex 中使用 ontoKBv2 skill/工具包，连接经认证的本地 ontology 服务，优先采用 MCP。harness 负责对话、计划及模型/工具循环，ontology 服务负责持久知识和执行约束。仅用 Codex 写代码、用 Codex 模型生成摘要，或在 CRUD 后台加一个聊天框，均不满足要求。

现有 ontoKB 的 `codex_backend.py` 已调用 `codex app-server`，`knowledge_agent.py` 已提供限定工具，可复用经验。若选择嵌入式外壳，可用 app-server 作为轻量 harness 客户端；目标不是在聊天框后自造一个独立 agent 循环。原生 Codex 集成为必需，嵌入外壳可选且另测。官方说明区分 exec、SDK、app-server：[Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)；会话/事件参考 [App Server](https://learn.chatgpt.com/docs/app-server)。固定并实测接口版本，验证账号和无人值守可用性，不能直接假定。

| 编号 | 必需的 harness 行为 |
|---|---|
| HR-01 | 通过 Codex 加工具完成收集、有据回忆、记忆审核/纳入、判断修改、内部任务和周回顾，无需强制网页后台。 |
| HR-02 | skills/指令、工具 schema、适配器、Codex 版本和模型配置均版本化；skill 教流程，工具服务执行权限。 |
| HR-03 | 宿主绑定可信拥有者/工作区/会话身份；工具输入不能提权。提供读取和限定 Action，不开放任意 SQL 或直接接触私库的无限 shell/文件能力。 |
| HR-04 | run ID、任务检查点、回执独立于对话保存；中断/重启/上下文压缩后读取权威状态并对账再继续；聊天摘要不是个人记忆，重放不得重复副作用。 |
| HR-05 | 支持用户中途调整、取消和限额；取消未提交工作，已提交 Action 仍可见，撤销需补偿；定时任务有明确范围/预算，不能升级为拥有者。 |
| HR-06 | 审批绑定具体 Action 参数、目标版本、执行者和到期时间；来源文本不能审批 Action；已授权低风险工作避免重复确认。 |
| HR-07 | 显示进度、证据、拟修改项和可观察结果，不要求私有思维链；回执/回读验证后才能声称成功，区分已提交副作用与随后自然语言回复失败。 |
| HR-08 | 测试登录过期、模型故障、协议不兼容、工具失败、取消、审批中断、会话混淆和注入；记录认证/计费模式，不把开发者账号分发给所有用户或假定人人可用。 |

典型任务：“保存这两篇文章，只显示不确定的抽取”“我上月如何判断，哪些新证据构成挑战”“把这个论断纳入记忆，立场保持未决定”“完成 T-17 任务”“生成本周回顾，不改变我的判断”。Agent 解析 ID、读取证据、预览重要修改并调用强类型 Action；验收检查实际操作，不只看回复措辞。

## 架构与部署要求

保留 LOGOS 的逻辑分层，以 Codex harness 为中心部署本地 ontology 工具服务和持久 worker。TypeScript 本体核心可复用 LOGOS domain/contracts 模式，ontoKB Python 解析器经有界适配器复用或逐步迁移；事实修改只有一个权威边界。可选 React 证据/审核面板消费同一契约，不能成为核心任务的必经入口。产品包包含服务依赖，并提供 Codex 前置条件与连接诊断；实施前确定技术栈和 harness 传输方案。

| 模块 | 职责与边界 |
|---|---|
| 接入与构建 | 获取允许的来源，保留快照，解析/切分/抽取候选并记录处理版本 |
| 本体注册与运行时 | 加载已校验本体包，验证对象/关系，授权并执行 Action，控制状态迁移 |
| 知识与回忆 | 读取有权限的当前或历史对象；按需组合关键词/向量检索、类型/时间查询及引用验证 |
| 个人记忆 | 管理审核、纳入、立场及修订历史，不与来源正确性混为一谈 |
| 审计与 worker | 持久保存任务、幂等键、执行回执和 outbox；崩溃后重放投影 |
| Codex skills 与工具适配器 | 提供对话工作流，将限定工具映射到 Function/Action，返回证据、run ID 和回执 |
| 可选视图与导出 | 显示证据/审核细节，将规范数据投影到 Obsidian 和搜索视图 |

本地默认采用 SQLite 外键、事务、迁移工具及应用层强类型校验作为权威数据源，来源快照存本地内容库，搜索索引可重建。将 LOGOS 持久化契约适配到本地存储，PostgreSQL/OpenSearch/MinIO 和多个 API 服务不是笔记本必装依赖。未来共享部署可在隔离/并发测试后使用服务器存储实现同一契约。采用 Neo4j 或增加图谱本身不等于实现企业级 ontology。

| 编号 | 运维要求 |
|---|---|
| NFR-01 | 交付有版本的 Windows skill/工具服务包，支持连接引导、启停、健康检查、更新/回滚及诊断；声明 Codex 支持版本及每用户登录前提；存储/工具运行时不依赖 GPU，本地模型另设预算。 |
| NFR-02 | 本地 API 默认只监听 loopback，对本地客户端认证、验证 origin、防止浏览器跨来源滥用修改接口；共享访问启用前必须有真正的服务端身份、权限和传输保护。 |
| NFR-03 | 凭证使用操作系统保护机制，不写入源码或导出包；配置远程模型前告知并取得数据外发配置同意；本地存储不等于本地推理；默认无遥测或云同步。 |
| NFR-04 | 存储、检索、缓存、日志、agent 工具隔离工作区；保护私密记忆字段和原文；说明删除范围和备份保留，不能宣称已删除离线备份内的数据。 |
| NFR-05 | 对象修改、版本递增、回执和 outbox 同事务提交；投影异步执行并展示待同步状态，支持重试和对账；投影失败不能显示笔记更新成功。 |
| NFR-06 | 支持加密备份，在全新工作区恢复并校验完整性，保留期限由用户控制；本地追加式审计不宣称能防机器管理员篡改。 |
| NFR-07 | 记录延迟、模型用量、失败任务、队列年龄、审核负担、来源时效和费用估算，诊断脱敏；输入大小、并发、重试及模型预算均有上限。 |

初始基准环境为 Windows 11、4 个物理 CPU 核、16 GB RAM、SSD；性能规模样例为 10,000 份文档、100,000 个对象/论断及 500,000 条关系。记录硬件和模型位置，规模样例仅证明性能而非精度。无推理时存储/工具及辅助证据视图应可用，harness/模型不可用时 Agent 任务明确报错。本地模型适配属于后续兼容选项，不宣称 Codex 支持所有本地模型或离线运行，必须独立测试质量和工具契约。

## 自动化与精度提升策略

自动完成采集、解析、候选抽取、确定性校验、低风险来源归属、去重、索引与回顾草稿；身份歧义、证据不足、冲突、schema 修改、破坏性操作及个人立场变化进入审核。用户应能批量处理有证据的提议，而不是手工编辑三元组。

采用可测覆盖率的风险/质量门。模型自报置信度不是经校准的正确率；阈值应在验证集上结合来源质量、证据精确对齐、类型约束、身份歧义、冲突及实际错误率确定。仅对符合条件的低风险来源断言，在证据完整且质量门通过时自动发布。“系统校验通过”表示通过这些检查，不表示独立核实为真。个人记忆默认由拥有者决定是否纳入；任何主动开启的自动纳入规则必须显式配置并单独审计，任何规则均不得合成用户立场。

以 Codex harness 加限定工具为起点，采用受约束抽取、确定性校验和关键词/类型检索；根据消融结果再加向量、重排、验证或更多检索轮次。优先改善解析、身份、证据和契约。初始问答最多 3 轮检索、8 次工具调用，含重试及工具执行总时限 30 秒；后台每阶段最多 3 次尝试、推理并发 2。上限可配置并记录，校验失败不能绕过。多 Agent 协作可选，须共享权限/预算并以实测收益证明必要性，不能替代核心单 Agent harness。

微调为可选项，不在交付关键路径。仅当标注错误显示稳定抽取弱点、数据授权清楚、导出/运行时兼容已验证时尝试；初始上限为 2 个工程日、1 次 adapter 训练及事先分配的计算预算。训练、开发、验收来源隔离，保留未微调基线。

## 测量及拟定验收目标

以下数字是拟定工程目标。基线摸底后、候选方案调优前，冻结范围、硬件、模型、提示词/本体版本及数字预算。后续变更须显式记录范围决策并重新评测，不得看到锁定集结果后降低门槛。

| 编号 | 指标及分母 | 初始门槛 |
|---|---|---|
| Q-01 | 正确类型数/匹配金标实体数；漏实体另计召回 | 类型准确率 >=97%；实体召回 >=90% |
| Q-02 | 正确关系/全部输出关系；正确关系/金标关系 | 精确率 >=97%；召回 >=85% |
| Q-03 | 正确自动合并对/全部自动合并对；同一身份金标对上的召回 | 合并精确率 >=99%；召回 >=80%；无已知严重错人合并 |
| Q-04 | 真正支持论断的引用/全部引用；有支持引用的事实分句/全部事实分句 | 引用精确率 >=98%；覆盖率 >=95% |
| Q-05 | 完整正确且有证据的回答/全部可回答问题，失败/超时仍在分母中 | 总体 >=90%；每个声明切片 >=85% |
| Q-06 | 正确澄清/拒答数除以全部缺证或歧义问题；无必要拒答/可回答问题 | 前者 >=95%；后者 <=5% |
| Q-07 | 正确自动发布低风险断言/全部自动发布断言；自动完成的合格来源/全部合格来源 | 精确率 >=99% 时自动化覆盖 >=70%；锁定评测至少 200 条自动发布断言 |
| Q-08 | 契约和故障用例中对无效、越权、过期、重复修改的处理 | 100% 用例结果正确；零越权写入、重复副作用、静默丢失 |
| Q-09 | 有效时间/记录时间回答正确数除以全部时间问题 | >=95%；冲突及立场历史关键用例全部通过 |
| Q-10 | 无开发人员协助的新手任务完成情况 | 5 人中至少 4 人在安装后 15 分钟内完成首次收集、带引用问答和记忆审核 |
| Q-11 | 指定环境、预热后、并发 1 的本地搜索、详情与完整引用回答 | p95 搜索 <=1 秒、详情 <=0.5 秒、回答 <=30 秒，含模型/网络时间 |
| Q-12 | 合格 2,000 英文词正文接入，中文按预先冻结的等量 token 档位测量；不含初次下载和 ASR | worker 并发 2 时 p95 <=120 秒；下载另计 |
| Q-13 | 稳定性、恢复及迁移 | 连续 24 小时无已提交数据丢失或无界积压；进程崩溃测试已提交本地事务 RPO 0；规模样例备份恢复 <=30 分钟 |

记录每来源、每回答、每日的 API/model token 用量及费用估算。拟定默认上限为每次标准 2,000 词接入 USD 0.10、每回答 USD 0.05、每日 USD 2；用户可使用前调整，评测前冻结。它们是预算上限，不是供应商报价，也不保证任何模型都能满足。计入重试和验证调用；到上限即停止新模型任务，订阅/本地不可按次计费的用量独立披露。记录磁盘及进程树内存；应用 RSS <=4 GB，本地模型/ASR 进程另设明确预算。

## 评测计划

准备至少 120 份获准或合成来源，覆盖中英及支持的格式；至少标注 1,000 个实体、1,000 条关系、200 对身份样例和 300 个问题。按来源家族/项目及其衍生论断划分 60 开发、30 验证、30 锁定验收来源，不能把相邻 chunk 分到不同集合。问题划分为 150/75/75，身份对为 100/50/50；必要时增加锁定标注量以达到自动发布样本门槛，小切片分母不得隐藏。覆盖复制/修订来源、同名、否定、数字、过期信息、冲突、个人立场、缺证和提示注入。另建 100 个确定性的 Action/权限/故障用例。

锁定集由两位评审标注并裁决实质分歧，拥有者确认个人记忆语义。路由前冻结自动化合格样本定义，不得把难例临时改成“不合格”以提高成绩；同时报告全体输入及合格输入上的拒绝/审核率。金标答案不得进入索引或提示词，证据来源按正常场景可检索。报告原始计数、置信区间、语言/来源/难度切片、版本、成本及全部失败。随机性质量评测以固定声明配置重复 3 次，不挑最好的一次。

在同样获准资料和尽可能相同的模型上对比现有 ontoKB 与 v2，披露差异。预先定义困难问题集，目标为有实质影响的有据回答错误相对减少至少 20%，且全部绝对门槛通过；若基线已零错误，实验前冻结审核时间降低等替代目标。消融本体校验、消歧、证据验证；图谱更好看不能作为改善指标。[验收计划](ACCEPTANCE_PLAN_ZH.md)规定关键失败和证据要求。
